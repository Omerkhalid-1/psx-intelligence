# Operations

## Processes

| Process | Command (local venv) | Health signal |
|---|---|---|
| API + dashboard | `.venv/bin/gunicorn -b 127.0.0.1:8000 -w 3 wsgi:app` (dev: `.venv/bin/flask --app wsgi run`) | `GET /api/v1/health` |
| Worker | `.venv/bin/celery -A app.tasks.worker:celery worker --loglevel INFO` | `celery_workers` in `/api/v1/health/dependencies` |
| Scheduler | `.venv/bin/celery -A app.tasks.worker:celery beat --loglevel INFO` | `scheduler` heartbeat (every 60 s, stale after 180 s) |

`/api/v1/health/dependencies` returns `ok`, `degraded` (DB up, something else down) or
`unavailable` (HTTP 503, DB down), plus the IDs of any stuck jobs.

The worker probe uses Celery's broadcast ping and waits for its full timeout
(`DEPENDENCY_CHECK_TIMEOUT_SECONDS`, 1 s), so the dependencies endpoint takes about 1 s by design.
Use `/api/v1/health` for load-balancer liveness.

## Database migrations

```bash
.venv/bin/flask --app wsgi db upgrade              # apply
.venv/bin/flask --app wsgi db downgrade -1         # roll back one revision
.venv/bin/flask --app wsgi db check                # fails if models and migrations differ
.venv/bin/flask --app wsgi db migrate -m "msg"     # new revision: review the generated file before committing
```

Review every autogenerated revision. Alembic does not drop PostgreSQL enum types in downgrades,
so add an explicit drop (see `6f60f0960c4f`). The test suite runs migrations from scratch on
every session.

## Jobs

- Submit: `POST /api/v1/jobs` (bearer token) or `flask --app wsgi submit-job system.self_check`.
- Status: `GET /api/v1/jobs/<id>`. `202 Accepted` means *recorded and dispatched*, not completed.
- `dispatch_failed`: the broker refused the message. Check Redis, then resubmit.
- **Stuck** (queued > 15 min or running > 65 min): the worker is down, the message was lost (e.g.
  Redis restarted), or the worker crashed outside the job wrapper. Fix the cause, then resubmit.
  Stuck rows are kept as history, not edited.
- Retries: only `TransientJobError`, at most `max_retries`, with exponential backoff.
- Worker restarts: `acks_late` + `reject_on_worker_lost` redeliver in-flight messages. The
  wrapper skips jobs that already finished, so redelivery is safe.

## Market data (psxdata-api)

**1. Run the psxdata-api service** (separate process, localhost only):
```bash
services/psxdata-api/run.sh          # first run installs pinned v0.5.0 into services/psxdata-api/.venv
curl http://127.0.0.1:8100/health    # {"data":{"status":"ok"},...}
```
In Docker: the `psx-api` compose service (`mtauha/psxdata-api:0.5.0`), reachable only on the
compose network. Swagger docs: `http://127.0.0.1:8100/docs`.

**2. Enable and load history** (`.env`: `PSXDATA_ENABLED=true`):
```bash
flask --app wsgi ingest-psx bars --full --sync     # backfill (about 10 years; under a minute for 5 symbols)
flask --app wsgi ingest-psx quotes --sync
```
Without `--sync` the command queues to a worker. Via the API (admin): `POST /api/v1/ingestion/runs`
with `{"dataset": "daily_bars"|"quotes", "full_history": bool, "symbols": [...]}`. It returns 409
while one is active and 429 within 60 s of the last run of that dataset.

**3. Schedule:** `ENABLE_SCHEDULED_INGESTION=true`, then run **beat and a worker**. Bars run
Mon–Fri at `PSXDATA_DAILY_SYNC_TIME` (PKT, after the close, incremental with a 10-day overlap).
Quotes run every `PSXDATA_QUOTE_POLL_INTERVAL_MINUTES` inside `PSXDATA_QUOTE_WINDOW`. Beat
crontabs use Asia/Karachi time.

**4. Inspect:** `GET /api/v1/ingestion/status`, `/api/v1/ingestion/runs[/<id>]` (per-symbol
outcomes and quarantined rejections), System health → Data sources, and
`GET /api/v1/health/dependencies` (`psxdata_api` dependency plus data freshness).

| Run error | Meaning / action |
|---|---|
| `provider_unavailable` | psxdata-api is down or PSX is unreachable (503). Start the service or wait; the next run retries. The dashboard keeps showing stored data |
| `upstream_data_error` | psxdata rejected PSX's data (502). Usually transient on PSX's side. If it persists, PSX's site changed: check for a psxdata release |
| `rate_limited` | over 60 requests/min. Raise `PSXDATA_REQUEST_SPACING_SECONDS` |
| `invalid_response` | the response format changed. Run the contract test and do not bump versions blindly |
| `partial` | some symbols failed or records were rejected. See the run's `request_metadata.symbols` |
| `abandoned` | a worker died mid-run. The next run took over |

**Contract test (run daily, or after any version bump):**
```bash
RUN_EXTERNAL_TESTS=1 .venv/bin/pytest -m external -s
```
It fails loudly if psxdata-api's response format changes. The scheduled daily bar sync also
fails visibly (failed run, dashboard and health warnings) if the format breaks.

**Upgrading psxdata-api:** change `PSXDATA_API_REF` in `services/psxdata-api/run.sh` and the
image tag in `compose.yaml` together, restart, and run the contract test.

## Refreshing to the latest information (manual)

One action fetches everything new and recomputes what depends on it:

1. **Live quotes** for the tracked stocks (indices have none).
2. **The daily research pipeline**:
   - fetches new daily bars from psxdata-api;
   - checks for a new market session;
   - refreshes news (Google News RSS, FinBERT scoring, daily aggregation).

   Only when a new session arrived does it go on to:
   - run the quality checks;
   - recompute the analysis summaries and features;
   - write that session's forecasts;
   - score forecasts that have matured.

| Where | How |
|---|---|
| Dashboard | **Refresh latest data** bar on every page. Enter `ADMIN_API_TOKEN`, then **Start refresh**. It shows progress and reloads the page when done. Needs a running Celery worker. |
| API (admin) | `POST /api/v1/refresh` with body `{}` and `Authorization: Bearer $ADMIN_API_TOKEN`. Returns 202 and a job to poll at `GET /api/v1/jobs/<id>`. |
| Terminal | `.venv/bin/flask --app wsgi refresh`. Runs inline, no worker needed, and prints the summary. |

**Guards**
- One refresh runs at a time. A second request while one is queued or running returns that job (200) instead of starting another.
- Requests within `REFRESH_COOLDOWN_SECONDS` (120 s) of the previous one get a 429, because every refresh sends requests to PSX and Google News.
- Quotes and the pipeline are attempted independently. A quote outage does not stop the bar and news refresh. Status is `succeeded`, `partial`, or `failed` (only if both parts failed).

**Behaviour**
- Running a refresh again with no new session is cheap. Bars and news are still checked; analysis and forecasts are left as they are (recorded as `skipped: no new session`).
- Forecasts are insert-only. A forecast is generated only for the session being processed, never back-filled for sessions that were missed, because a back-filled forecast would not be a genuine live forecast.

**Token handling**
- The dashboard keeps the admin token in page memory.
- It stores the token in `sessionStorage` (that tab only) only if **Remember in this tab** is ticked.
- The token is sent only as an `Authorization` header to this app's own API.

## Adding a symbol to the watchlist

Each tracked symbol gets daily bars, quotes, the analysis engine and its own website page. Indicators are
only meaningful on a split/bonus-adjusted price series, so a new symbol is not "done" until its corporate
actions are recorded.

1. **Check the listing**: `GET /api/v1/symbols/search?q=<SYMBOL>`. The symbol must be a current PSX listing.
2. **Add it** to `PSXDATA_SYMBOLS` in `.env`, and its sector to `config/watchlist.yaml` (display only).
   Leave `MODEL_SYMBOLS` alone: the forecasting models were validated only on that set.
3. **Backfill** `flask --app wsgi ingest-psx bars --full --sync --symbols <SYMBOL>`, then restart the web and worker processes.
4. **Find discontinuities**: `flask --app wsgi research quality`, then list open `unexplained_discontinuity`
   errors for the symbol (`GET /api/v1/data-quality/issues?symbol=<SYMBOL>&severity=error`).
   Each one is an ex-entitlement day: a bonus issue, split or large cash dividend.
   - **Suspected** (warning) jumps at exactly −7.5% are usually limit-down days; leave them.
5. **Research each error** in public sources: the company's or PSX's notices, or the financial press.
   Record it in `config/corporate_actions.yaml` with its sources:
   - `bonus` or `split`, with `share_multiplier` (and `cash_dividend_per_share` if paid in the same event): these adjust prices.
   - `cash_dividend`, with multiplier 1: this only explains the drop and never adjusts prices.
   - Use `status: unverified` when the ex-date is inferred only from prices.

   Never record an action you cannot source. If a symbol has events you can't verify, leave it off the watchlist.
6. **Sync and verify**:
   - `flask --app wsgi research sync-corporate-actions --actor <you>` must report `"inconsistent": []`.
   - Re-run `research quality`: no unexplained errors should remain for the symbol.
   - `GET /api/v1/engine/diagnostics` must show no failures.

The 2026-10-21 expansion followed this process. MTL, SEARL, ENGROH, POL and ILP were tried and dropped:
their histories contain bonus, rights or restructuring events that could not all be sourced. Their stored
bars are unused.

**Live quotes.** psxdata-api builds quotes from the PSX screener, which does not cover every listed symbol
(currently DGKC, OGDC, PPL, HUBC and PSO). A quote sync records these as "no live quote available" without
failing. Their pages use daily bars.

## Logging

JSON lines on stdout (`LOG_FORMAT=json`), or human-readable text (`LOG_FORMAT=text`, the
development default). Set `LOG_FILE` to also write a rotating file (10 MB × 5). Key fields:
`timestamp, severity, environment, service, component, message, correlation_id, job_id,
analysis_module, symbol, source_id, event_type, duration_ms, status, error_category`. Trace a
request across API and worker by `correlation_id`. Logs are operational and may be rotated.
Durable history lives in `job_runs` and `audit_events`.

## Backup and restore (PostgreSQL)

```bash
pg_dump --format=custom --no-owner -d "$PG_URL" -f psx_$(date +%Y%m%d).dump
createdb psx_restore && pg_restore --no-owner -d psx_restore psx_YYYYMMDD.dump
```

(`PG_URL` is `DATABASE_URL` without the `+psycopg` driver suffix.) Redis needs no backup (ADR-002).
**Not yet rehearsed.** A restore drill is a Phase 8 deliverable.

## Recovery

| Situation | Action |
|---|---|
| Redis lost | Restart Redis. Jobs in flight show as stuck. Resubmit them. |
| Worker crash mid-job | Message redelivered automatically. The job's partial writes were rolled back. |
| Failed migration | Transactional DDL in PostgreSQL rolls back. Fix the revision and rerun `db upgrade`. |
| Partial ingestion (Phase 2+) | Ingestion is idempotent per file/batch. Rerun the same input. |
